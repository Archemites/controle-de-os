# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Two HTML pages — no build step, no bundler — for "Teraup Soluções". Cada página é markup puro; o CSS e o JS foram extraídos para arquivos próprios (idênticos ao que era inline, sem nenhuma mudança de lógica):

```text
index.html         →  css/index.css         +  js/index.js
app_pedidos.html   →  css/app_pedidos.css   +  js/app_pedidos.js
```

**O repositório é publicado no GitHub Pages**, então a raiz contém apenas o que o site serve — `index.html`, `app_pedidos.html`, `css/`, `js/`, `.nojekyll` (impede o Jekyll de processar/ignorar arquivos) e `.gitignore`. Tudo que é só de desenvolvimento local vive em [dev/](dev/): `dev/server.js`, `dev/simulate_app.js` e `dev/xlsx/`. `index.html` é o antigo `app_medicoes.html` (com `css/app_medicoes.css` → `css/index.css` e `js/app_medicoes.js` → `js/index.js`); a aba "Controle de Medições" nas duas páginas aponta para `./` em vez de um `.html`, para funcionar igual na raiz do Pages e no servidor local. Como as duas páginas são 100% client-side (planilhas entram por file picker, tudo persiste em IndexedDB), não há nada de backend para portar.

Os três `<script>` de cada página (xlsx-js-style, pdf.js e o script local) usam `defer`, então baixam em paralelo sem bloquear o parse e executam **em ordem de documento** antes do `DOMContentLoaded` — por isso o código local pode continuar consultando o DOM no topo do arquivo e usando os globais `XLSX`/`pdfjsLib` sem esperar por nada. Não remova o `defer` de um só dos scripts: a ordem xlsx → pdf.js → script local é o que garante os globais. O `<head>` também traz `preconnect`/`dns-prefetch` para `cdn.jsdelivr.net`. `dev/server.js` já serve `.css`/`.js` com o MIME correto e é genérico quanto a subpastas, então nada nele precisou mudar.

- [index.html](index.html): view and append rows to an existing "Medições Enviadas" (measurements sent) Excel spreadsheet, entirely client-side, using SheetJS loaded from a CDN. Supports editing/adding rows and exporting an updated `.xlsx`.

**Both pages load `xlsx-js-style@1.2.0`, not the official `xlsx@0.18.5`.** It is a community fork of SheetJS 0.18.5 that exposes the same global `XLSX` and the same API, but additionally **writes** `cell.s` (cell styles). The official community build parses `cell.s` on read and silently discards it on write, so cell styling — including the centered alignment on export — never reached the output file. Don't swap back to `xlsx@0.18.5` without removing the `centralizarCelulas()` calls, or the centering will silently stop working again. Note the fork's *reader* still does not reconstruct `cell.s`, so verifying alignment by reading the exported file back in Node will always report `undefined`; inspect `xl/styles.xml` (`<cellXfs>`) and the `s=` attributes in `xl/worksheets/sheet1.xml` instead.
- [app_pedidos.html](app_pedidos.html): viewer for the "Controle Pedidos de Compra" spreadsheet ([dev/xlsx/Controle Pedidos de Compra.xlsx](dev/xlsx/Controle%20Pedidos%20de%20Compra.xlsx)) — import, search, sort, totals row, a manual "Adicionar Pedido" modal to add rows in-memory, and a "Baixar planilha" button that exports all currently loaded rows (imported + manual) to a standalone `Controle de Pedidos de Compra.xlsx`. No edit-existing-row form, and the export does not write back into the originally-imported workbook object — it builds a fresh one from `rows`.

Both pages share a browser-tab-style `#appTabs` bar at the top (`.app-tab` links) so the user can switch between the two "services" without leaving the app; each page links to the other's `.html` file. They also share the `medicoes_tema` localStorage key so light/dark mode stays in sync across both tabs, but use **separate** IndexedDB autosave databases (`medicoes_autosave` vs `pedidos_autosave`) since they hold different workbooks.

`dev/simulate_app.js` is a Node-based test harness that replicates `index.html`'s read/write logic against the real spreadsheet in [dev/xlsx/](dev/xlsx/) to verify output without opening a browser. It requires the local `xlsx` npm package (see `node_modules/`). There is no equivalent harness for `app_pedidos.html` since it has no write-back logic to test.

`dev/server.js` is a zero-dependency static file server used to serve the app over `http://localhost` instead of `file://`. This is required for the IndexedDB-based autosave to work: Chrome treats every `file://` page load as a unique security origin, so IndexedDB writes from one load are invisible on the next (autosave silently "disappears" on refresh). Serving from `http://localhost` gives a stable origin across reloads. It serves any file under the repo root generically (`ROOT = path.join(__dirname, '..')`, já que o script mora em `dev/`), então adicionar páginas não exige mexer em rotas. Usado só em desenvolvimento — no GitHub Pages quem serve os arquivos é o próprio Pages, e a origem `https://` também dá um IndexedDB estável.

## Running / testing

- **Install dependencies**: `npm install` (fetches `xlsx`/`xlsx-js-style`, usados só pelo harness Node em `dev/`; as páginas carregam o `xlsx-js-style` do CDN e não dependem de `node_modules`).
- **Run the app**: `npm start` (= `node dev/server.js`), depois abra `http://localhost:5500` (carrega `index.html`; use a barra de abas ou abra `http://localhost:5500/app_pedidos.html` direto). O servidor tem `ROOT = path.join(__dirname, '..')`, ou seja, serve a raiz do repositório a partir de `dev/`. Do NOT open either HTML file directly via `file://` — autosave (IndexedDB) does not persist across reloads in that mode. Use the "Importar Medições" / "Importar Pedidos" button to load the respective `.xlsx` (this still uses a native file picker, unaffected by the server).
- **Publicar no GitHub Pages**: basta apontar o Pages para a branch/raiz do repositório — não há build. `dev/` e `node_modules/` são inertes lá (o `node_modules` está no `.gitignore`).
- **Test the read/write logic without a browser**:
  ```
  npm run simulate
  ```
  This reads the source workbook, appends one synthetic row using the exact same cell-writing code path as `baixarPlanilha()` in the HTML file, and writes the result to `dev/output_simulado.xlsx` (gitignored; `SRC`/`OUT` são caminhos relativos a `__dirname`, não mais absolutos de uma máquina específica). Inspect the resulting file's `O.S` column formatting, date serials, and column widths to confirm round-trip fidelity.

## Architecture

### index.html

Toda a lógica vive em [js/index.js](js/index.js) (estilos em [css/index.css](css/index.css); o `.html` é só markup). The logic in `dev/simulate_app.js` is a near-exact copy of the same cell-writing code, kept in sync manually — when changing the write logic in the HTML file (`baixarPlanilha()`), mirror the change in `dev/simulate_app.js` if you want the Node-based test to stay representative. **`dev/simulate_app.js` still models the old append-into-the-imported-workbook export** and has not been updated for the column-subset rewrite described below; it exercises the cell-typing/number-format rules, not the current export shape.

Key flow:
1. **Load** (`fileInput` change handler): reads the `.xlsx` via SheetJS, finds the header row (the row whose first cell is `"O.S"`), and parses all subsequent non-empty rows into `rows` (objects keyed by the `COLUMNS` array) via the shared `construirLinhas()` helper. If a workbook is already loaded, a modal (`importModalOverlay`) asks the user to choose "Substituir lista atual" (replace — calls `carregarWorkbookDeBytes`, discarding the previous workbook) or "Adicionar à lista existente" (append — `extrairLinhasDeBytes` parses the new file's rows without replacing the active `workbook`, and pushes them into both `rows` and `newRows` so they're written out on the next download alongside manually cadastradas rows).
   - **Every import resets column visibility**: `carregarWorkbookDeBytes()` sets `visibleColumns = new Set(COLUMNS)` (plus `salvarVisibilidadeColunas()` + `renderColumnsPanel()`) so all columns are shown again after loading a base spreadsheet, even if the user had unchecked some previously. The "adicionar à lista existente" path doesn't go through this function and keeps the current selection.
   - **`__linha` (row identity)**: `construirLinhas()` stamps each parsed row with its 0-based index in the source sheet. The autosave stores `newRows` (which includes *edited original rows*), and the restore path re-parses the original `.xlsx` bytes — without a stable identity the edited copy was pushed alongside the freshly-parsed original, so editing a não-faturado row produced a duplicate on every reload. `carregarWorkbookDeBytes()` now replaces the matching `__linha` row instead of pushing. Rows coming from a *different* file (append-import, "adicionar mesmo assim") get `__linha` deleted, and "substituir o existente" inherits the replaced row's `__linha`.
   - **Trash / deleted rows (`lixeira` + `linhasExcluidas`)**: the per-row trash button does **not** delete — `excluirLinha()` moves the row into the `lixeira` array as `{ linha, excluidoEm }`, drops it from `rows`/`newRows`, and (for rows that came from the file) adds its `__linha` to `linhasExcluidas` so the restore path doesn't resurrect it when it re-parses the original `.xlsx` bytes. Both are persisted in the autosave record, and `carregarWorkbookDeBytes(data, fileName, rowsExtras, excluidas, lixeiraSalva)` takes them as its 4th/5th arguments (it filters the freshly-parsed rows by `linhasExcluidas` and skips `rowsExtras` entries whose `__linha` is excluded). `purgarLixeira()` — called on load *and* on every `renderTable()`, so the deadline applies without any user interaction — permanently discards items older than `LIXEIRA_DIAS` (30). Importing a base spreadsheet resets the trash, like everything else.
   - **Uppercase normalization**: text/code fields are always forced to `UPPERCASE` — on import (`construirLinhas()`), on manual cadastro/edit (`salvarMedicao()`), and on data written by the PDF reader (both into the medição row and into the pedido created in `app_pedidos.html`'s autosave via `criarPedidoNoControle()`). `COLS_MAIUSCULAS` (`"O.S"`, `"Mês Envio Medição"`, `"GAP"`, `"Engenheiro Acesso"`, `"Projetista"`, `"Regional"`, `"Pedido de Compra"`) lists which columns get this; dates and currency columns are untouched. `app_pedidos.html` mirrors this inline in its own `construirLinhas()`, `addSaveBtn` handler, and PDF-reader handler for `"Número Pedido"`/`"O.S"`/`"Cliente"`/`"Gap"`/`"Observação"`.
   - **`normalizarOs()` — toda O.S numérica tem 10 dígitos**: definida nos dois apps (idêntica), força `padStart(10, '0')` em qualquer valor composto **só de dígitos** e deixa passar intacto o que for misto (`"GAP-36613"`, `"0021214728/0021214746"`, `"AMP-4866/0030871575"` — completar esses com zeros destruiria a informação). Aplicada na importação (`construirLinhas()` em ambos), no cadastro/edição manual (`salvarMedicao()` / `addSaveBtn`), no preenchimento vindo da sincronização com Pedidos e no leitor de PDF (`padOs()`, que agora também padroniza para 10 dígitos sempre, em vez de só quando o valor não começava com `"00"`). Na base real isso já é o formato de 921/921 O.S das Medições e 152/152 dos Pedidos; a função existe para que nada entre fora do padrão por digitação, PDF ou planilha de terceiros.
   - **Zero-padding on `O.S`/`Pedido de Compra`**: these columns are numeric cells with a zero-padding `number_format` in the source file (e.g. `21214728` displayed as `"0021214728"`). `sheet_to_json(..., { raw: true })` returns the raw numeric value `v`, silently dropping that padding. `construirLinhas()` (used by both `carregarWorkbookDeBytes` and `extrairLinhasDeBytes`) compensates by reading each cell in these two columns directly off the worksheet via `valorCelulaComPadding()`, preferring the formatted text `w` over the raw value whenever the cell is numeric and `w` starts with a leading zero. Don't revert to plain `sheet_to_json` output for these columns without preserving this.
   - On append, rows are checked for duplicates against the existing list (and against other rows in the same imported file) via `encontrarLinhaDuplicada()`, which checks **exact O.S match first** (`mesmaOs()` — O.S is the row's real identity everywhere else in the app: `hasPedido`, `linhasPelaOs`, `sincronizarComPedidos`...) and only falls back to counting shared non-empty field values across all `COLUMNS` except the derived `"Custo Total"` (`contarCamposIguais()`) when no row shares the same O.S — a row is treated as a duplicate there once it matches on `MIN_CAMPOS_IGUAIS_DUP` (2) or more fields, e.g. same `"Pedido de Compra"` and same `"Regional"`. **The O.S-first check is load-bearing, not an optimization**: the fallback heuristic alone is too weak on this dataset — `"Ano"`/`"Mês Envio Medição"`/`"Regional"` and the near-universal `"R$ -"` in `"Custos Diversos"`/`"Custo ART"` are common enough that re-importing the same 933-row file matched 932 rows to the *wrong* existing row before this fix (see [TESTE_DE_FOGO.md](TESTE_DE_FOGO.md)). Non-duplicates are added immediately; duplicates are queued (`filaDuplicados`) and reviewed one at a time in the `dupModalOverlay` modal, which lists which fields matched and shows the existing vs. incoming row side by side (values escaped via `escapeHtml()` — see the XSS note below). For each, the user picks "Substituir o existente", "Adicionar mesmo assim" (keep both), or "Não adicionar este" — optionally checking "aplicar a todos os demais" to apply the same choice to the rest of the queue without further prompts. **That "aplicar a todos" path resolves the remaining queue in a loop, not recursion** (`mostrarProximoDuplicado()`/`aplicarAcaoDuplicado()` used to call each other one stack frame per item, which overflowed the call stack around 4,000–5,000 forced duplicates — a plausible size when consolidating historical spreadsheets).
1b. **Ações column (edit / delete)**: `renderTable()` appends an extra `<th class="acoes-col">Ações</th>` / `<td class="acoes-cell">` **after** the visible columns, with an icon-only pencil button (`openFormParaEdicao(row)`) and an icon-only trash button (`excluirLinha(row)`, which asks for confirmation via `window.confirm()` before removing anything). This column exists **only on screen** — it is not in `COLUMNS`, so `baixarPlanilha()` never emits it; the totals row just gets a trailing empty `<td>` to keep the column count aligned. Editing (button *and* double-click on the row) is enabled on **all tabs**, not just Sem Pedido / A Cobrar as before — hence the edit modal title is plain "Editar Medição". Both buttons `stopPropagation()` so a single click doesn't fall through to the row.
1c. **Lixeira tab**: a 5th sub-tab (`tabLixeira`, `activeTab === 'lixeira'`) listing the trashed records with an extra "Excluído em" column (deletion date + days left) and its own two actions: a restore arrow (`restaurarDaLixeira()` — puts the row back into `rows`/`newRows` and clears its `__linha` from `linhasExcluidas`) and the trash icon (`excluirDefinitivo()`, permanent, confirmed). `renderTable()` branches into `renderLixeira(visibleCols)` for the body, hides the totals row and the search bar, and `linhasVisiveis()` is not consulted at all — trashed rows are outside `rows`, so they never affect search, totals or any export. `atualizarEstadoDownload()` disables the download button while this tab is active (`NOMES_ABAS.lixeira` exists only for the label). They carry **no text and no emoji** — the glyphs are inline-SVG constants (`ICONE_LAPIS`/`ICONE_LIXEIRA`, defined right above `renderTable()` in each file) stroked in `currentColor`, so the pencil picks up the neutral button color and the trash the red one from `.row-btn.excluir`, in both themes.
1d. **Cell values are HTML-escaped before hitting `innerHTML`**: every `<td>` built in `renderTable()`/`renderLixeira()` (both apps) and every field shown in the duplicate-review modal (`renderCampoDup()`, Medições only) passes through `escapeHtml()` — previously only used for the PDF-reader results panel. Without it, a cell containing markup (an imported `.xlsx` from a third party, or just a manually-typed field — text fields are only uppercased, never sanitized) executes as HTML/JS the moment the row renders, since none of these fields have any other input validation. Don't build a row's `<td>` string from a raw field value again without routing it through `escapeHtml()` first.
2. **Add a row** (`salvarMedicao`): builds a row object from the sidebar form and pushes it into both `rows` (for display) and `newRows` (rows pending write-out). SLA days and "Custo Total" are auto-computed client-side. Both the cadastro and edição paths end with `sincronizarComPedidos({ avisar: false })` so a freshly typed/edited row is complemented from the Controle de Pedidos immediately, without waiting for the next import/refresh. Editing a row (`editingRow` branch) also does `delete editingRow.__sincronizados` — the form just rewrote every field by hand, so any earlier "filled by sync" marker (see point 5b below) no longer applies.
3. **Sort** (`renderTable`/`toggleSort`): every visible `<th>` is clickable and cycles ascending → descending → unsorted, tracked in the `sortCol`/`sortDir` globals. `sortKey()` coerces per column type — dates to timestamps, `"Mês Envio Medição"` to calendar order via `MESES_ORDEM` rather than alphabetically, `O.S`/`Pedido de Compra`/`Ano`/SLA to numbers (stripping `R$` and pt-BR thousand/decimal separators so legacy text-formatted cells still sort numerically), everything else to a lowercased string compared with `localeCompare('pt-BR', {numeric:true})`. **Currency columns route through the shared `valorNumerico()`** (not the same regex as the code columns above) specifically so the accounting-zero string `"R$ -"` sorts as `0` instead of as an empty cell — it used to use its own inline regex, under which `parseFloat("-")` is `NaN` and every `"R$ -"` row silently sank to the bottom of the sort regardless of direction (`app_pedidos.html`'s `sortKey()` already did this right; only Medições had the bug — see [TESTE_DE_FOGO.md](TESTE_DE_FOGO.md)). Empty values always sink to the bottom regardless of direction. Sorting is display-only — it's applied to the filtered `visibleRows` copy and does not affect the order `newRows` is written out in. `valorNumerico()` is the shared currency parser (also used by `fmtCurrency`, the sort keys, and the totals row below); it handles legacy rows stored as formatted text (`"R$ 1 278,82"`, thousands separated by a non-breaking space) and maps the accounting-zero string `"R$ -"` (1375 occurrences) to `0` rather than NaN.
4. **Export** (`baixarPlanilha`): **exports only the columns currently checked in the column filter** (`visibleColumns`), in `COLUMNS` order, **and only the rows the active tab currently shows** — it calls the shared `linhasVisiveis()` helper (tab filter + search + current sort), the same one `renderTable()` uses, so each tab downloads its own spreadsheet. The filename and the sheet name carry the tab label from `NOMES_ABAS` (`Medições Enviadas - <aba> - Teraup Soluções.xlsx`), the download button's text/title are re-rendered per tab by `atualizarEstadoDownload()` (called from `setActiveTab`), and the export **no longer calls `limparAutosave()`** since it's now a partial export and the local draft stays the only complete copy. Because the output is a column *subset*, it no longer mutates the imported `workbook` — it builds a brand-new workbook (`aoa_to_sheet([colsExport])` + per-cell writes from `rows`, so imported *and* manually cadastradas rows are included), mirroring `app_pedidos.html`'s approach. **Row 1 is a totals row** (a live `SUM(<col><first>:<col><last>)` formula with `z: 'R$ #,##0.00'` for each exported column in `COLS_SOMATORIO`, blank otherwise — mirroring the on-screen `totalsRow`, same approach as `app_pedidos.html` but placed *above* the header), row 2 is the header, data starts row 3; `lastOriginalRow`/`newRows`-append logic is no longer used by the export. **`"Sla Envio Medição"` é recalculado na exportação via `slaAtual(rowObj)`**, igual à tela — antes o export lia `rowObj[col]` cru e emitia o número gravado na planilha de origem (frequentemente `0`/vazio), fazendo uma medição enviada em 01/08 sair com 0 dias. Number formats are reinforced per cell (`NUMERIC_CODE_COLS` (`O.S`, `Pedido de Compra`) are **written as text** — `{t:'s', v: String(val), z:'@'}` — preservando exatamente o texto lido da célula, inclusive os zeros à esquerda, em vez de reconverter para número + máscara `'0000000000'`; `CURRENCY_COLS` → `'R$ #,##0.00'` via the shared `valorNumerico()` so legacy text-formatted values become real numbers, `DATE_COLS` → `'dd/mm/yyyy'` via `excelSerialFromDate()`), and `!cols` widths are taken from the `LARGURAS_COLUNAS` constant indexed by `COLUMNS.indexOf(col)` (18 entries — the source sheet's 18 physical columns; `COLUMNS` covers the first 17, the trailing `"Cobrança Medição"` being the excluded one). `centralizarCelulas(ws)` still runs before `XLSX.writeFile(..., { cellStyles: true })`.
   - **The download button is disabled when no column is checked** — `atualizarEstadoDownload()` sets `downloadBtn.disabled = !workbook || visibleColumns.size === 0` (plus an explanatory `title`). It's called after every mutation of `visibleColumns` (each checkbox `change`, "Mostrar todas", "Ocultar todas", initial load) and in place of the old unconditional `downloadBtn.disabled = false` on workbook load.
5. **Leitura de PDF** (`abrirLeituraPdf` / `pdfInput` change handler): the "Leitura de PDF" topbar button opens `pdfModalOverlay` and a native `.pdf` picker. `extrairTextoPdf()` uses **pdf.js (`pdfjs-dist@3.11.174`, loaded from CDN alongside SheetJS; `GlobalWorkerOptions.workerSrc` points at the matching CDN worker)** to concatenate the text of every page into one whitespace-normalized string, entirely client-side. `procurarCamposNoTexto()` then runs the `PDF_CAMPOS` regex table over it, looking for `O.S` (run through `padOs()`, which strips non-digits and left-pads to 10 with zeros when the PDF prints the number without the leading `00`), `GAP`, `Pedido de Compra`, `Valor Faturado`, `Data` and `Cliente` — in the PDFs, "Nº/Número do Pedido" *is* the Pedido de Compra and "Valor Líquido" *is* the Valor Faturado, so each pair is a single `PDF_CAMPOS` entry whose regex accepts both labels; each hit is listed in the modal (misses shown as "não encontrado"). The main action (`pdfUsarBtn`, "Atualizar não faturado + criar pedido") does two things: (1) `linhaPelaOs()` finds the row with the same O.S **restricted to the não faturados** (`!hasPedido(r)`, digits-only comparison) and writes `GAP`, `Pedido de Compra` and `Valor Faturado` into it — already-faturado rows are never touched by the PDF reader — pushing it into `newRows` so the change survives the export; and (2) `criarPedidoNoControle()` **always** creates a new record in the Controle de Pedidos de Compra, writing it straight into that app's `pedidos_autosave` IndexedDB (`manualRows` in the `estado`/`atual` record — same origin, different DB), so it shows up when that tab is opened/reloaded. If Pedidos has no autosave yet (no spreadsheet imported there), the write is skipped and `fileStatus` says so. **Duplicates are always flagged before anything is written**: more than one não-faturada row with the same O.S prompts a `confirm()` (only the first would be updated), and a pedido whose Nº do Pedido or O.S already exists in the target `manualRows` prompts another — `criarPedidoNoControle()` returns `{criado, duplicado, motivo}` and `fileStatus` reports which branch happened. The same Nº-do-Pedido/O.S duplicate check runs in `app_pedidos.html` before pushing a new row. When no não-faturado row matches, `pdfUsarBtn` is **disabled right after the read** (with a `title` and an extra "Sem O.S para atualizar" line in the results list explaining whether the PDF had no O.S at all or the O.S isn't among the não faturados), so **nothing is updated** — the reader does not create a medição nor pre-fill the cadastro form; only step 2 (the pedido) happens, with whatever the PDF carried. `Cliente` and `Número do Pedido` have no field in the Medições sheet, so they are display-only (the latter is used as a fallback for `f_pedido`). `Valor Faturado` is the exception to the label-regex approach: in the purchase orders it is the **last column of the item table** ("… Preço Líquido  Valor Líquido", numbers only on the item line), so `extrairValorLiquido()` (a `PDF_CAMPOS` entry with `extrai` instead of `re`) slices the item block after that header, up to the tax lines (`CBS1`/`IB1S`/`Total`), and sums the numbers with **exactly 2 decimals** — Qt.Pedido has 3 and Preço Líquido has 6, so each item line contributes only its Valor Líquido. It falls back to a `Valor Faturado/Total/da Nota:` label regex for other document layouts. `Cliente` uses `extrairCliente()`: the client name always follows the protocol on the circuit line (`Circuito: … - PROTOCOLO: 202530482590-1 - UNIDAS LOCADORA S A`), so it takes whatever comes after the protocol code and its separator (`-` or `/`), cut at the next document block (`Valor`, `Circuito`, `CNPJ`, `Item`, …), and **only that** — there is deliberately no `Cliente:`/`Razão Social:` fallback, so a PDF that doesn't carry the name in that exact shape reports "não encontrado" rather than guessing. `osPelaGap()` cross-references the GAP read from the PDF against the already-loaded list (`rows`): it fills in the `O.S` when the PDF doesn't carry one (noted as "identificada pela GAP na lista") and, when both exist but differ, keeps the PDF's value and flags "atenção: a GAP aponta para a O.S … na lista". The note lives in `pdfCamposLidos['_osOrigem']` and shows up in the modal (it is excluded from the "N de 6 campos encontrados" count). `Data` likewise uses `extrairData()`: the order's date sits just below "Nº do Pedido" as `Data: 18.04.2026` (dots, not slashes), so the labelled field wins over any other date in the document (e.g. `Dt.Remessa`), with a "first date anywhere" fallback, normalized to `dd/mm/aaaa`. The other regexes are heuristics tuned to Portuguese-labelled orders/notes — widen `PDF_CAMPOS` rather than adding parallel parsing code.
5b. **Sincronização automática com o Controle de Pedidos de Compra** (`sincronizarComPedidos()`): roda sozinha ao fim de `carregarWorkbookDeBytes()` (via `setTimeout(…, 0)`, para não atropelar a mensagem de `fileStatus` do chamador — cobre tanto a importação quanto a restauração do autosave), depois de cada uso da leitura de PDF, e depois de cada cadastro/edição manual em `salvarMedicao()` (as três últimas com `{ avisar: false }`, já que não há uma mensagem de import pra anexar o aviso). **Linhas complementadas ganham um destaque visual na célula** que foi preenchida: cada campo escrito por `sincronizarComPedidos()` é anotado em `row.__sincronizados` (array de nomes de coluna, só em memória — não é lido em nenhuma outra lógica nem sai na exportação), e `renderTable()` aplica a classe CSS `cel-sincronizada` (`css/index.css`, fundo + barra lateral em `--accent`) mais um `title` explicativo na célula correspondente. A marca é apagada quando a linha é editada manualmente (`delete editingRow.__sincronizados` em `salvarMedicao()`) — o formulário acabou de reescrever todos os campos à mão, então "veio do sync" deixa de fazer sentido. `lerPedidosDoControle()` abre o IndexedDB `pedidos_autosave` (mesma origem), **reparseia os `fileBytes` da planilha de pedidos** com a mesma detecção de cabeçalho de `app_pedidos.js` (linha cujo índice 3 é `"O.S"` ou índice 1 é `"Número Pedido"`, fallback 2), aplica `linhasExcluidas`/`linhasEditadas` e concatena os `manualRows`. `indexarPedidos()`/`pedidoDaMedicao()` ligam pedido ↔ medição por **O.S → Número Pedido → GAP** (`soDigitos()` nos dois primeiros, maiúsculas no terceiro; primeiro pedido vence em caso de empate). Duas guardas descobertas no teste de fogo ([TESTE_DE_FOGO.md](TESTE_DE_FOGO.md)) são load-bearing: `soDigitos()` **também remove os zeros à esquerda** (a mesma O.S aparece como `0021214728` nas Medições e `21214728` nos Pedidos — sem isso pares legítimos deixam de casar, sem erro visível), e o casamento por Número Pedido/GAP é **descartado quando as duas O.S existem e divergem** (GAPs se repetem entre O.S diferentes na base real e colavam o `Pedido de Compra` de outra O.S). `lerPedidosDoControle()` filtra itens não-objeto de `manualRows` (um `null` num autosave antigo derrubava a sincronização inteira com `TypeError`). O preenchimento cobre **todas as medições, faturadas e não faturadas** (ao contrário do leitor de PDF, restrito aos não faturados) e é **aditivo**: `CAMPOS_PEDIDO_MEDICAO` mapeia `Número Pedido → Pedido de Compra`, `Valor → Valor Faturado`, `Gap → GAP`, `O.S → O.S`, e cada campo só é escrito quando está vazio na medição — nada preenchido é sobrescrito. Valores de `CURRENCY_COLS` passam por `valorNumerico()`, os demais viram `UPPERCASE`. Linhas alteradas entram em `newRows` (para saírem na exportação) e disparam `renderTable()` + `agendarAutosave()`. A planilha de pedidos nunca é modificada por esse caminho.
6. **Totals row** (`totalsRow`, populated in `renderTable`): a sticky row under the header sums `"Valor Medição Enviadas"`, `"Valor Faturado"`, `"Custo Total"`, `"Medição Terceiros"`, `"Custos Diversos"`, and `"Custo ART"` (`COLS_SOMATORIO`) using `valorNumerico()`, computed over `visibleRows` — so it always reflects whatever the active tab/search/filters currently show, not the full dataset. Cells where `valorNumerico()` returns `NaN` (blank, `"R$ -"`, or any non-numeric text) are skipped rather than added as 0, so they don't silently distort the total.

Important constraints baked into the write logic — preserve these if touching `baixarPlanilha()` or the load handler:
- **Column order/definition**: `COLUMNS` array must match the exact column order of the source spreadsheet (its first 17 columns). `"Cobrança Medição"` is the source sheet's 18th column, excluded from both `COLUMNS` and the form; since the export now builds a fresh sheet from `COLUMNS ∩ visibleColumns`, it is no longer emitted as a blank trailing column.
- **Cell typing per column** via `CURRENCY_COLS`, `DATE_COLS`, `TEXT_COLS` (`GAP` only), and `NUMERIC_CODE_COLS` (`O.S`, `Pedido de Compra`) — these decide whether a cell is written as Excel date serial, number, or string.
- **Number formats and column widths are manually reinforced** after both read and write, because SheetJS's community build does not reliably preserve `!cols` widths or custom `number_format` (e.g. the zero-padded `"0000000000"` format on `O.S`) through a read→write round trip. Don't remove this reinforcement code — it's compensating for a known SheetJS limitation, not dead code.
- **Centered alignment on export** (`centralizarCelulas(ws)`, called right before `XLSX.writeFile(..., { cellStyles: true })` in both apps): walks every address in the sheet's `!ref` and merges `{ horizontal: 'center', vertical: 'center', wrapText: false }` into `cell.s.alignment`, preserving any existing style. Requires the `xlsx-js-style` fork (see top of this file) and the `cellStyles: true` write option — both are load-bearing.
  - **Only cells that exist are centered.** Blank fields are written as *no cell* (the sheet's blank-cell convention), so they keep Excel's default alignment until typed into. In the Medições sheet that is ~199.750 of 227.718 grid slots. Two rejected fixes, for the record: column-level `!cols[c].style` is dropped by `xlsx-js-style` (it emits `<col>` widths with no `style=` attribute), and materializing the blanks as `{t:'s',v:''}` cells does work but grows the export from ~2,8 MB to ~10,4 MB (vs. 0,22 MB for the source file) and breaks the blank-cell convention. `t:'z'` placeholder cells are not written out at all.
- **Completely empty records are always dropped**, in both apps: `linhaVazia(row)` filters rows out in `construirLinhas()` on import, and `linhasVisiveis()` / `renderTable()` purges any that appear later (edits, autosave restore) from `rows` + `newRows`/`manualRows` — so they never reach the screen, the autosave, or the export. In `index.html`, `linhaVazia()` also treats a row as garbage when every one of `"O.S"`, `"Envio Medição"`, `"Pedido de Compra"`, `"Valor Medição Enviadas"`, `"Valor Faturado"` is blank, even if every other `COLUMNS` value is technically non-blank — the source spreadsheet trails off into ~11.7k "phantom" formula rows carrying garbage only in `"Ano"`/`"Sla Envio Medição"` (e.g. `Ano: 2026`, `Sla: 46231`, everything else null), which the plain all-`COLUMNS`-blank check didn't catch and which were flooding "Sem Pedido"/"A Cobrar" with blank-looking lines.
- Empty/null field values are written as *no cell* (deleted), matching the blank-cell convention of the original spreadsheet, rather than as empty-string cells.

Reads sheet `PEDIDOS DE COMPRA`, header row is row 3 (0-based index 2 — found dynamically by `carregarWorkbookDeBytes()` scanning for a row whose column-index-3 cell is `"O.S"` or whose column-index-1 cell is `"Número Pedido"`, falling back to index 2).

- Search filters on `O.S`, `Número Pedido`, `Gap`, `Cliente`. Sort (`sortKey()`/`compareRows()`/`toggleSort()`) mirrors the Medições app's approach (dates → timestamps, `Valor`/`O.S`/`Número Pedido` → numbers, else lowercased string `localeCompare('pt-BR', {numeric:true})`), applied to `visibleRows` only (display-only, doesn't mutate `rows`). - **Sub-tabs + Lixeira**: this page previously had no tabs; it now carries a two-button `#subTabs` bar ("Pedidos" / "Lixeira", CSS copied from `index.html`) driven by `abaAtiva` + `setActiveTab()`. Restoring a row that came from the file re-adds it to `linhasEditadas` (and removes its `__linha` from `linhasExcluidas`); a manual/PDF row goes back into `manualRows`. `lixeira` is persisted in the `pedidos_autosave` record and restored via the 5th argument of `carregarWorkbookDeBytes()`.

Double-clicking a row also opens the edit modal. Not part of `COLUMNS`, so `baixarPlanilhaPedidos()` ignores it.
  - Since this file re-parses the original `.xlsx` on autosave restore, imported rows now carry a `__linha` (their 0-based index among the sheet's data rows, stamped by `construirLinhas()`), and the autosave record gained `linhasExcluidas` (array of deleted `__linha`) and `linhasEditadas` (the edited row objects). `carregarWorkbookDeBytes(bytes, fileName, excluidas, editadas)` filters out the excluded rows and overwrites the matching `__linha` rows with the edited copies. Manual/PDF-created rows have no `__linha` — they're already persisted whole in `manualRows`.
- **Adicionar Pedido (manual add)**: the "+ Adicionar Pedido" button next to "Importar Pedidos" opens `addModalOverlay`, a form covering all 7 `COLUMNS`. Requires a workbook to already be loaded (`abrirModalAdicionar()` blocks with an `alert()` otherwise, since there's nowhere meaningful to persist rows before an import establishes the autosave record). On save, the row is pushed into both `rows` (display) and the separate `manualRows` array, then `salvarAutosave()` persists `manualRows` alongside `fileBytes`/`fileName` in the `pedidos_autosave` IndexedDB store. Manually-added rows are not written into the originally-imported `.xlsx` bytes — they live only in-memory + autosave, and reappear on reload via `restaurarAutosaveNaAbertura()` re-applying `estado.manualRows` on top of the freshly re-parsed original rows. Importing a new file (`carregarWorkbookDeBytes()`) resets `manualRows = []`, since it's a fresh load. Currency (`Valor`) is parsed via the shared `valorNumerico()`; date (`Recebimento Pedido`) is stored as a `Date` (structured-clone-safe in IndexedDB), matching the type shape of imported rows so `fmtCurrency`/`fmtDate`/`sortKey`/totals-row all treat manual rows identically to imported ones.
- **Leitura de PDF**: the same pdf.js-based reader as `index.html` (module copied verbatim — `PDF_CAMPOS`, `extrairValorLiquido`/`extrairData`/`extrairCliente`; keep the two copies in sync when tuning the regexes). Downloaded filename is literally `Controle de Pedidos de Compra.xlsx`.
  - **Totals row (row 2) uses a live Excel formula, not a static number**: for each column in `CURRENCY_COLS` (currently just `Valor`, column D), the cell is written as `{ t: 'n', v: <soma>, f: 'SUM(C3:C160)', z: 'R$ #,##0.00' }` — **the cached `v` is mandatory: SheetJS silently drops any cell that has only `f` and no `v` on write**, which makes the whole totals row disappear from the exported file (column letter + row range computed from `rows.length`) so the sum recalculates in Excel if the user edits values after opening the file, mirroring the on-screen `totalsRow`.
